# Agent Note: Memory across windows, task hand-over, and session deletion

Status: implemented

English | [中文](2026-09-14-memory-cross-window-and-continuation.zh.md)

## Problem

With the [memory tools and the per-step recall](2026-09-13-engineering-memory-harness-face.md) in place, three things were still only implied by the design. Cross-window behaviour: window A saves or corrects an entry — when does window B see it, what happens to a request B has already started, and can a window that read an older version write over the newer one? New-session continuation: a note of "where the task stands" had no shape, so a later session could not tell a confirmed decision from an open item, or a check that passed yesterday from one that holds today; and the tempting shortcut — harvesting compaction summaries into long-term memory — would turn transient context into standing facts. Deletion: the plan fixed the rule (a saved memory is independent of its source; nothing re-reads a deleted session) but nothing implemented it, and "enhanced memory off" had no state a session could act on.

## Decision

**Cross-window chain.** Nothing new was built for it; the existing pieces were made to keep their promises and were proven against two independent production Sessions. One Harness process serves every window and the store's in-memory state is its persisted state, updated only after the backend acknowledged a write, with writes serialized. A step reads that state once, at its start, in the `agent/pre-step` listener, and a list once sent is the request's list: so window A's save, correction or forget is what window B's next user step recalls (a replacement list with the new version, or the empty replacement after a forget), and a turn already under way keeps its list through its later tool steps. The one hole was closed: `memory_correct` and `memory_forget` used to fall back to the live version when the model omitted `expectedVersion`, which let a window that read v1 write over another window's v2. `expectedVersion` is now required — the version the model saw in the recalled list or a tool result — and a stale one is refused with the current one; the Remote methods already required the version the page read. `workbench-memory/change` is forwarded to the browser through the application's remote assembly so the pages of every window re-read; a restart reopens the domain from disk and another DSH home is another store.

**Continuation notes.** A hand-over has one shape, `ContinuationNote`: `goal`, `decisions` (what the user confirmed), `unfinished` (planned, failed or unverified work goes here), `leads` (files, commands, places to look first), `verified` (only what was actually run or checked, with its result). It is stored as ordinary entry content in a fixed text layout (`Goal:`, `Decided:`, `Unfinished:`, `Leads:`, `Verified then:`, `- item` lines, `(none)`), so the pages edit text while the tools and the recall read the parts back apart; free text that is not in the layout stays a plain continuation line. The note is bounded — 24 items per part, 512 bytes per item, no `<system-reminder>` or recall header inside, no item starting with a note label — so a note never nests a recalled list or another note and never grows without bound. `memory_remember` takes it as the structured `continuation` argument for `kind: 'continuation'` and refuses free content for that kind (and the note for other kinds); `memory_correct` rewrites a note whole. The recall renders a note as a block that names its session, its date and its five parts, under a group title that says these are old summaries, that "Verified then" is past, and that nothing is resumed until the user asks; the guide tells the model how to continue an earlier task: recall the notes, check the disk and Git, report, wait. Compaction summaries are deliberately not harvested into notes: a note exists when a session saved one, the session log stays the Harness's only record of a session, and after a compaction shadowed an injected list the next user step re-sends one — the compaction engine keeps tool call and result pairs whole, and the summary never becomes an entry.

**Off, and deletion.** The injection mode gains `off`: from the next step nothing is injected — neither the entries nor, silently, the legacy files — and every tool refuses in the result the model reads; the entries stay for the next `entries`. The workbench plugin's legacy section now yields text only when the mode is exactly `markdown` (or the service is absent). On `session/content-deleting`, the entries the session wrote — live and kept-aside — are marked `source.sessionDeleted: true` and kept; the mark is metadata (no version bump, so no open window's quoted version goes stale), survives corrections, undos and restores, is listed through `list({ sessionId })` for the deletion dialog, and shows as `since deleted` in a recalled note. Nothing re-reads or copies the deleted session; a session deleted before the domain opened is logged and left unmarked, and a mark the backend refuses is logged and never blocks the deletion. The plan's rule for auto-derived notes (delete them with the source) has no population, since nothing derives notes.

## Alternatives considered

**Harvesting compaction summaries into continuation notes.** Rejected: the phase's brief forbids turning a continuation summary into long-term memory automatically, and a summary claiming "tests passed" would have become a standing fact; the Harness's session log already keeps the summary where it belongs.

**A second reader over other sessions' logs.** Rejected: it would be a copy of session content in this package; the session log, its query and its recovery are the Harness's, and the guide points the model there when no note exists.

**Guessing the version from the live entry when the model omits it.** Rejected (it was the P7 behaviour): it is exactly the write-over the cross-window rule forbids; a required argument costs the model one retry at most.

**A Config `enabled: false` for "off".** Rejected in favour of the stored `off` mode: a composition flag cannot be toggled from a page and would have been a second source of truth beside the slot.

**Hard-deleting entries with their source session.** Rejected: a saved memory is the person's, independent of where it was written; the mark says the source is gone, and forgetting stays their explicit act.

## Consequences

The tests drive two independent production Sessions on separate scripted adapters through the real loop and capture every request: B recalls A's write on its next user step and A's correction as a declared replacement, B's stale correction is refused with the current version and A's content stands, A's forget empties B's next list, a turn blocked inside a tool keeps its list while A writes and swaps on the next user step, two projects share a preference and keep their facts apart, a restart over the same home finds the entry and the mode while another home has nothing, `off` injects neither list nor guide and refuses the tools until `entries` returns, and a deleted session's entries stay marked (live and forgotten, through correct/undo/restore) with a warning instead of a block when a mark cannot persist. The note codec round-trips and refuses every unbounded or nested form; a brand-new session reads a hand-over with its parts apart and the past framing, and lists notes on request; the real compaction engine shadows an injected list and the next step re-sends exactly one, pairs whole, store unchanged. The pages that show the marks, offer `off` and edit notes are the interface phase's work.
