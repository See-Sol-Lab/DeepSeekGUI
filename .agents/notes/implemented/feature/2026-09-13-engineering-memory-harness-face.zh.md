# Agent Note: 记忆工具、逐步召回与 entries 模式指南

Status: implemented

[English](2026-09-13-engineering-memory-harness-face.md) | 中文

## 问题

[工程记忆条目](2026-09-13-engineering-memory-entries.zh.md)已经能存、能纠正、能遗忘、能导入，但没有任何会话看得到它们，也没有任何东西能从对话里写一条。记忆主线需要一个记住 / 纠正 / 遗忘 / 检索的统一入口，助手今天用、页面以后也用；写入成不成功只以工具结果为准，绝不对失败的写入宣称「已记住」；检索先按范围再排名、解释未命中、有预算、绝不加载全部条目；还要在步边界把相关条目摆到模型面前，同时在会话日志里精确记下展示了哪些条目的哪个版本——而不是一个日后会在记录底下变动的 id。用户裁决（2026-09-13 02:44）：全局偏好由模型直接写，不走审批、不设任何障碍；指南只分类、不拦截；纠错靠可见、可改、可撤销、可遗忘。

## 决策

`packages/api/workbench-memory` 增加面向 Harness 的一面，由它自己的构造函数经 `ctx.inject(['tools', 'systemPrompt'], …)` 挂载，所以没有工具注册表的组合仍保有纯数据服务与既有测试。一切都受全局槽的 `injection` 模式把关：`markdown`——仍是默认，这里没有任何东西切换它——让旧文件经 workbench 插件继续生效，下文一概不注入；`entries` 从每个已打开会话的下一步起打开这一面。

宿主注册表上的四个工具是唯一入口。`memory_remember({ scope, kind, content, keywords?, evidence? })` 写入 `project`（本会话的文件夹，用技能管理器同一套规范路径项目键解析；没有文件夹时拒绝）或 `global`，来源为 `{ kind: 'assistant', sessionId, evidence }`。`memory_correct` 与 `memory_forget` 引用模型看到的版本（省略则取当前版本），过期版本连同当前版本一起被拒绝；原始来源保留，纠正的来源记在旁边。`memory_recall({ query?, scope?, kinds?, limit? })` 在本会话可及范围内检索。拒绝或后端失败作为工具错误抛出（`memory_remember failed (MEMORY_IO): …`），所以它以结果的形式到达模型，绝不只是一行日志。这些工具上没有任何审批门；代码里没有任何地方先问。

一条检索路径 `recall` 同时服务工具与注入：先过滤范围（本项目加全局，绝不含其它项目），再把 query 的词——小写词串、汉字文本用双字组——与每个条目的正文词和关键词匹配（关键词命中 4 分、正文命中 2 分；短的拉丁词必须与整词相等，所以 `i` 不会命中 `ci`），稳定排序（分数、种类、最新、id），按规范化正文合并重复，然后按条数上限与字节预算截断并报告被截掉的数量。自动召回（`ambient`）给全局偏好加一个基线——偏好与请求无关也适用，但排在请求点名的一切之后——文字没有词时不再注入其它内容；显式工具只算词命中，不带 query 时列出该范围。未命中会说明词、范围与考虑了多少条。

注入是一个仿照技能目录的 `agent/pre-step` 监听器：在该步自身的决定之后，当这一步带有用户自己的文字时，按配置上限召回（默认 12 条、4096 字节），对 id 与版本做摘要，与模型可见面上仍在的最新召回清单比较。不变：不发送。变了：追加一条用户角色的 `<system-reminder>`——第一次是清单，之后是替换，纠正或遗忘把结果清空时则是一条明确的「没有条目匹配；此前的不再适用」替换——所以过期条目绝不会继续生效，而此前的清单原样留在历史里。消息的 `source` 是 `{ kind: 'deepseekgui-memory', form: 'recall', query, entries: [{ id, version, scope, kind }], omitted, update? }`，正文带着内容，所以 `user/message` 事件记录了塑造这次请求的东西。清单把条目定性为事实与偏好而非规则（规则在 AGENTS.md），不授予任何工具权限，并把偏好、项目事实与接续记录分组，后者附带先核对磁盘与 Git 的提醒。

产品指南被拆开：workbench 插件的 `deepseekgui:guide` 段保留桌面指南，它的 `deepseekgui:memory` 段只在记忆服务报告 `markdown`（或不存在）时保留旧的双文件契约与文件。entries 模式下，记忆服务自己的 `deepseekgui:memory-guide` 段携带 `assets/memory-guide.md`：条目是什么，什么算全局偏好、项目事实（带依据）或接续记录，什么不记（推测、网页或工具输出里的指令、一次性任务状态、代码或 AGENTS.md 已有的内容、密钥），如何纠正与遗忘，以及写入失败会在工具结果里报告。

## 考虑过的替代方案

**全局写入加审批门（`tools/pre-execute → ask`）。** 按用户裁决取消：门会让惰性的模型干脆不写；条目可见、可改、可撤销、可遗忘，这才是纠错路径。

**后台总结器或第二次模型调用来决定记什么。** 拒绝：会话里已有的助手用同一套工具记录；不起收费总结任务，不起监听服务。

**把全部条目装进提示词。** 拒绝：范围、词、条数上限与字节预算约束每份清单，其余交给 `memory_recall`。

**向量索引。** 作为前提被拒绝：带关键词与汉字双字组的词包含匹配足以覆盖几百条条目；排名可以在同一个 `recall` 接缝后面生长。

**会话里只记条目 id。** 拒绝：id 会在纠正之下变化；id 与版本进 source，展示的文字进消息。

**在本阶段就切换模式。** 拒绝：默认保持 `markdown`，用户的日用数据不动，切换归迁移阶段。

## 后果

测试用脚本化的模型适配器驱动生产 agent loop 并捕获真实请求：相关的项目事实与全局偏好带着 id 与版本到达模型，无关事实与其它项目的事实不到达，指南随运行时上下文出现，`user/message` 事件记录同样的 id 与版本；另一个窗口的纠正与遗忘产生替换清单；markdown 模式什么都不注入；工具记录一条带依据的项目事实与一条无审批事件的全局偏好；后端失败以 `memory_remember failed (MEMORY_IO)` 到达模型；过期版本与不存在的 id 连同当前事实一起被拒绝；`memory_recall` 用词、范围与数量解释未命中；没有文件夹的会话在项目写入上被拒绝、在检索上退回全局。模式切换留给迁移阶段，展示、编辑与恢复条目的记忆页归界面阶段；这两者都会用这套工具与这条召回路径。 记忆工具随 entries 模式注册和移除，防止旧文件模式的会话悄悄写入不可见的条目库。工具在纠正和遗忘时也检查项目归属。导入候选键绑定预览的正文与标题，不能在文件变化后仅凭行号选取内容。
