# Agent Note: 跨窗记忆、任务交接与会话删除

Status: implemented

[English](2026-09-14-memory-cross-window-and-continuation.md) | 中文

## 问题

[记忆工具与逐步召回](2026-09-13-engineering-memory-harness-face.zh.md)就位之后，还有三件事只停留在设计的暗示里。跨窗行为：窗口 A 保存或纠正一条条目——窗口 B 什么时候看到它、B 已经开始的一次请求会怎样、读到旧版本的窗口能不能盖掉新版本？新会话接续：「任务做到哪了」的记录没有形状，之后的会话分不清确认过的决定与未完成项，也分不清昨天通过的检查与今天仍成立的事实；而那条诱人的捷径——把压缩摘要收割成长期记忆——会把临时上下文变成常驻事实。删除：方案定了规则（保存下来的记忆独立于来源；不重读被删会话），却没有实现，「关闭增强记忆」也没有一个会话能据以行动的状态。

## 决策

**跨窗链路。** 没有为它新造任何东西；只是让既有部件兑现承诺，并在两个独立的生产 Session 上验证。一个 Harness 进程服务所有窗口，存储的内存态就是持久化态，只在后端确认写入后更新，写入串行。一步在开始时于 `agent/pre-step` 监听器里读一次这个状态，发出去的清单就是那次请求的清单：所以窗口 A 的保存、纠正或遗忘就是窗口 B 下一个用户步召回到的东西（带新版本的替换清单，或遗忘后的空替换清单），已经开始的一轮在后续工具步里保持自己的清单。唯一的漏洞被堵上：`memory_correct` 与 `memory_forget` 原来在模型省略 `expectedVersion` 时退回当前版本，这让读到 v1 的窗口能盖掉另一窗口的 v2。现在 `expectedVersion` 必填——模型在召回清单或工具结果里看到的版本——过期版本连同当前版本一起被拒绝；Remote 方法本来就要求页面读到的版本。`workbench-memory/change` 经应用的远程装配转发到浏览器，每个窗口的页面据此重读；重启从磁盘重开域，另一个 DSH home 是另一个存储。

**接续记录。** 交接只有一种形状 `ContinuationNote`：`goal`、`decisions`（用户确认过的）、`unfinished`（打算做、失败或未验证的工作归这里）、`leads`（文件、命令、先看哪里）、`verified`（只写真正跑过或查过的东西及其结果）。它以固定文本布局（`Goal:`、`Decided:`、`Unfinished:`、`Leads:`、`Verified then:`、`- item` 行、`(none)`）存成普通条目正文，所以页面编辑文本，而工具与召回把各部分分开读回；不符合布局的自由文本仍是一行普通接续条目。记录受约束——每部分 24 项、每项 512 字节、内部不得出现 `<system-reminder>` 或召回头、项不得以记录标签开头——所以记录绝不嵌套召回清单或另一份记录，也不会无限增长。`memory_remember` 对 `kind: 'continuation'` 以结构化的 `continuation` 参数接收记录并拒绝自由正文（其它 kind 则拒绝记录）；`memory_correct` 整条重写记录。召回把记录渲染成写明会话、日期与五个部分的块，组标题说明这些是旧摘要、「Verified then」已成过去、用户开口前不恢复任何工作；指南告诉模型如何接续早先的任务：召回记录、核对磁盘与 Git、报告、等待。压缩摘要有意不被收割成记录：记录只在会话保存过时存在，会话日志仍是 Harness 对一个会话的唯一记录，压缩遮蔽掉一份注入清单后下一个用户步只重发一份——压缩引擎保持工具调用与结果的配对完整，摘要绝不变成条目。

**关闭与删除。** 注入模式增加 `off`：从下一步起什么都不注入——条目不注入，旧文件也不会悄悄顶上——每个工具都在模型读得到的结果里拒绝；条目留着等下一次 `entries`。workbench 插件的旧记忆段现在只在模式恰为 `markdown`（或服务不存在）时产出文本。在 `session/content-deleting` 时，那个会话写的条目——存活的与搁置的——被标上 `source.sessionDeleted: true` 并保留；标记只是元数据（版本不动，所以没有哪个打开的窗口引用的版本会过期），经纠正、撤销与恢复都保留，经 `list({ sessionId })` 供删除对话框列出，在召回的记录里显示为 `since deleted`。没有任何东西重读或复制被删除的会话；域打开之前被删除的会话只记日志、不做标记，后端拒绝写入的标记也只记日志、绝不阻塞删除。方案里对自动派生记录的规则（随来源删除）没有适用对象，因为没有任何东西派生记录。

## 考虑过的替代方案

**把压缩摘要收割成接续记录。** 拒绝：本阶段指令禁止自动把接续摘要变成长期记忆，一份声称「测试通过」的摘要会变成常驻事实；Harness 的会话日志本来就把摘要留在它该在的地方。

**再造一个读其它会话日志的读取器。** 拒绝：那等于在本包里复制会话内容；会话日志、它的查询与恢复归 Harness，没有记录时指南把模型指向那里。

**模型省略版本时从当前条目猜版本。** 拒绝（这是 P7 的行为）：它正是跨窗规则禁止的覆盖；一个必填参数至多让模型重试一次。

**用 Config `enabled: false` 表示「关闭」。** 拒绝，改为存储在槽里的 `off` 模式：组合标志无法从页面切换，而且会成为槽之外的第二个事实源。

**随来源会话硬删除条目。** 拒绝：保存下来的记忆是人的，独立于它写在哪里；标记说明来源已不在，遗忘仍是人的显式动作。

## 后果

测试用两个独立的生产 Session 分别挂在各自的脚本化适配器上驱动真实 loop 并捕获每次请求：B 在下一个用户步召回 A 的写入、把 A 的纠正作为声明的替换收到，B 的过期纠正连同当前版本一起被拒绝而 A 的内容不动，A 的遗忘清空 B 的下一份清单，在工具里阻塞的一轮在 A 写入期间保持自己的清单、到下一个用户步才更换，两个项目共享偏好而各守事实，同一 home 上重启后条目与模式俱在而另一个 home 空空如也，`off` 既不注入清单也不注入指南并拒绝工具直到 `entries` 回来，被删会话的条目保留并带标记（存活与遗忘的，经 correct/undo/restore），标记写不进去时只警告不阻塞。记录编解码往返一致并拒绝所有越界或嵌套的形式；全新会话把交接的各部分分开读到并带着「已成过去」的框架，按要求列出记录；真实压缩引擎遮蔽注入清单后下一步恰好重发一份，配对完整，存储不变。展示标记、提供 `off` 与编辑记录的页面归界面阶段。
